1 · 系统架构

四个后端服务各司其职，共享 MySQL 与 Redis。只有 WebSocket 服务直接连闲鱼。
要点：只有 WebSocket 服务直接连闲鱼，其余服务通过内部 API 协作。 依赖顺序为 MySQL/Redis → Backend-Web → WebSocket → Scheduler。

2 · 消息自动处理流程

买家发来消息后，经过五道校验才决定回不回、怎么回。这是系统最核心的链路。
风控提示：reply_delay_seconds 字段默认为 0，即买家一发消息机器人立刻回。 这是最容易被判定为机器人的特征，建议改成 3~8 秒的随机值。

3 · 账号登录与 Cookie 续期

登录态是整套系统的地基。Cookie 失效时先走接口续期，失败再启动浏览器兜底。
要点：Cookie 续期有两条路——先试轻量接口，失败才启动浏览器（开销大、易触发验证）。 续期时带随机抖动，避免多台账号在同一时刻刷新。

4 · 定时任务链路

Scheduler 服务按各自周期执行，是自动发货和返佣铺货的驱动来源。
风控提示：返佣的「定时发布 + 定时删除」是闲鱼重点打击的批量行为模式。 当前发布与删除的间隔是固定值（5 秒 / 2 秒），建议改成随机区间，降低被算法识别的概率。

订单与自动发货链路

从订单触发到卡券送达的完整链路，含四道防重与拦截关卡。
四道防重关卡：冷却期检查 → Redis 分布式锁 → 本地锁（降级）→ 禁止发货规则引擎。 任何一道命中都会中止发货，目的都是避免同一订单把卡券重复发给买家。
5 类禁止发货规则（命中则拒绝发货，并可能关闭订单仅发卡券）： 买家信用为零 · 买家已有订单 · 全局已下单 · 买家未确认收货 · 个人黑名单。 规则在 delivery_rules/rule_registry.py 中注册，新增规则只需在那里加一行。
卡券三种来源：own 自有卡券 · dock_l1 对接货源一级 · dock_l2 对接货源二级。 多规格商品会先拉取订单的规格信息再匹配对应卡券。
